## 2. Анализ сетевой активности (Network Waterfall Analysis)

При исследовании вкладки Network выявлены три ключевые точки оптимизации:

### Проблема 1: Отсутствие Bulk-эндпоинта для массовых операций

- **Симптом:** При массовом изменении статуса выделенных задач отправляется серия отдельных HTTP-запросов к каждой задаче (`/15/`, `/14/`, `/13/` ... `/6/`).
- **Анализ Waterfall:**
  - Запросы выполняются параллельно, общее время завершения операции для 10 задач достигает **378 ms**.
- **Причина:** На фронтенде массовый экшен перебирает выбранные ID в цикле и вызывает точечный эндпоинт обновления для каждого элемента.
- **Влияние:** При выборе 50+ задач браузер упрется в лимит одновременных соединений (обычно 6 штук), из-за чего часть запросов встанет в очередь (Queueing), а нагрузка на сеть и бэкенд выростет экспоненциально.
- **Решение:** Реализовать на бэкенде единый эндпоинт `POST /tasks/bulk-update/` (или `PATCH /tasks/`), принимающий массив ID `[15, 14, 13, ...]` и новый статус за один HTTP-запрос.

---

### 🚨 Проблема 2: Критическая задержка авторизации (`POST /token/` — 923 ms)

- **Симптом:** Запрос получения токена авторизации `token/` выполняется **923 ms** (почти 1 секунду).
- **Анализ Waterfall:** ~99% времени занимает **Waiting (TTFB)** — задержка ответа бэкенда.
- **Причина:** Высокая сложность хэширования пароля (Cost Factor в Bcrypt/Argon2) на сервере или долгие синхронные операции при аутентификации.
- **Влияние:** Заметная задержка для пользователя при каждом входе в систему.
- **Решение:** Оптимизировать параметры хэширования и запросы к БД на бэкенде.

---

### 💡 Проблема 3: Клиентская пагинация при загрузке (`GET /tasks/`)

- **Симптом:** Запрос `GET /tasks/` возвращает сразу полный массив всех задач пользователя.
- **Влияние:** При росте количества задач у пользователя от 1,000+ элементов объём загружаемых данных значительно увеличится, что приведёт к задержкам при первичной загрузке страницы.
- **Решение:** Перейти на серверную пагинацию (передавать `page` и `page_size` в параметрах запроса).

## Backend Performance Metrics (W8) — Redis Caching (Cache-Aside)

### Архитектура и формат ключа

- **Стратегия:** Cache-Aside с TTL 60 секунд.
- **Хранилище:** Redis (База данных №1, отдельная от брокера Celery).
- **Формат ключа в Redis:** `tasks_service:user:{user_id}:tasks:{normalized_query_string}`
- **Отказоустойчивость:** Настроено `IGNORE_EXCEPTIONS=True` (при падении Redis приложение не падает, а автоматически переключается на запросы в PostgreSQL).

### Результаты замеров (Cache MISS vs Cache HIT)

| Метрика                     | Cache MISS (Первый запрос)                   | Cache HIT (Повторный запрос из кэша) |
| :-------------------------- | :------------------------------------------- | :----------------------------------- |
| **Время ответа (TTFB)**     | ~160–250 мс                                  | **~15–30 мс**                        |
| **Количество SQL-запросов** | 4 запроса (с учетом prefetch/select_related) | **0 запросов**                       |
| **Заголовок `X-Cache`**     | `MISS`                                       | `HIT`                                |

### Выводы

Внедрение кэширования списка задач в Redis снизило нагрузку на реляционную базу данных до нуля при повторных запросах пользователя в пределах 60 секунд. Безопасность и изоляция данных соблюдена за счет привязки ключа к `user_id` и нормализации параметров сортировки/фильтрации.

## 2. Архитектурные решения и защита от race conditions

### Выбор версионирования ключей вместо `delete_pattern`

- **Проблема `delete_pattern`:** Удаление по маске использует команду `SCAN` (или `KEYS` в старых версиях), сложность которой $O(N)$ растет с ростом числа ключей в базе, создавая нагрузку на однопоточный Redis.
- **Преимущество версионирования:** Инкремент ключа версии пользователя (`cache.incr`) выполняется за $O(1)$. Старые закэшированные записи просто перестают запрашиваться и автоматически удаляются по истечении своего TTL.

### Защита от гонок через `transaction.on_commit`

Инвалидация кэша (инкремент версии) выполняется строго после завершения транзакции в PostgreSQL:

```python
transaction.on_commit(lambda: bump_user_tasks_version(user_id))
```
