## 3. Выводы и потенциал оптимизации

1. **Главная проблема списка задач (Score 47):** Монструозный компонент `data-table` из Naive UI вместе со службами `dialog` и `message` блокирует главный поток (TBT 610 ms) и затягивает LCP до 6.6 s.
2. **Модальное окно:** Не вызывает сдвигов вёрстки (CLS = 0) и не блокирует поток при отображении.
3. **План оптимизаций:**
   - Разбить роуты и тяжёлые UI-компоненты на асинхронные чанки (`defineAsyncComponent` / dynamic `import()`).
   - Проверить точечные импорты для Naive UI и `lodash-es`, чтобы избавиться от лишнего кода.

## 4. Подробный аудит топ-5 зависимостей

1. **Naive UI (`n-data-table`, `n-select`, `n-modal` и др.):**
   - **Где используется:** Во всех формах, модалках и таблице задач.
   - **Нужна ли на первом экране:** Только базовая часть (Input/Button на странице авторизации). Таблица `data-table` на первом экране не нужна.
   - **Альтернатива / Оптимизация:** Настроить tree-shaking через `unplugin-vue-components` и вынести тяжелые компоненты (таблица) в асинхронные чанки (`defineAsyncComponent`).

2. **`lodash-es`:**
   - **Где используется:** Утилиты фильтрации и сортировки в сторе задач и компонентах пагинации.
   - **Нужна ли на первом экране:** Нет.
   - **Альтернатива / Оптимизация:** Заменить импорты всего пакета на точечные (например, `import debounce from 'lodash-es/debounce'`) или переписать на встроенные методы JS (`Array.prototype.filter/map/sort`).

3. **`date-fns`:**
   - **Где используется:** Форматирование дат создания/обновления задач.
   - **Нужна ли на первом экране:** Нет (на авторизации дат нет).
   - **Альтернатива / Оптимизация:** Перейти на точечный импорт используемых функций (`format`, `parseISO`) и явно подгружать только одну локаль `ru` / `en-US`, исключив лишние.

4. **Axios:**
   - **Где используется:** HTTP-клиент в API-слое (`src/api`).
   - **Нужен ли на первом экране:** Да, для запроса авторизации.
   - **Альтернатива / Оптимизация:** Оставить (объём ~13 KB оправдан), либо в будущем рассмотреть нативный `fetch`.

5. **Vue Core & Vue Router (`@vue/runtime-core`, `vue-router`):**
   - **Где используются:** Базовый каркас приложения и роутинг.
   - **Нужны ли на первом экране:** Да, критически необходимы.
   - **Альтернатива / Оптимизация:** Оставить. Базовый рантайм неделим.

### Ответы на ключевые вопросы ТЗ

1. **Почему `:key="item.id"`, а не `:key="index"`?**
   - При виртуализации элементы списка не пересоздаются с нуля, а **переиспользуются** при прокрутке.
   - Ключ `index` обманывает Vue: он считает, что компонент на позиции 0 не изменился. Это приводит к рассинхронизации локального состояния (состояние чекбоксов, инпутов, фокусов и CSS-анимаций).
   - Использование уникального и стабильного `item.id` гарантирует корректное обновление контекста строки при ресайклинге.

2. **Ограничения виртуализации:**
   - **Поиск `Ctrl + F`**: Браузер не находит элементы, отсутствующие в DOM. _(Требуется встроенный JS-поиск)_.
   - **Динамическая высота**: Требует постоянных замеров высоты через `ResizeObserver` (`DynamicScroller`), что сложнее математически.
   - **Доступность (a11y)**: Экранные дикторы не могут зачитать весь список, так как в DOM присутствуют только видимые узлы.
   - **Сброс скролла**: При переходах между роутами позицию скролла нужно сохранять в Pinia/Router state.

### Стратегии обработки длинных списков

- **Пагинация**: Для больших данных с бэкенда, когда важна индексация SEO или прямые ссылки на страницы.
- **Бесконечная прокрутка (Infinite Scroll)**: Для лент новостей и соцсетей до 300–500 элементов.
- **Виртуализация**: Для массивных списков в памяти (1 000+ элементов) со сложной версткой карточек.

### Анализ точечных оптимизаций Vue

1. **Prop Stability (Стабильность пропсов)**:
   - Передача вычисленного состояния (например, `:is-selected="task.id === selectedId"`) вместо передачи всего объекта состояния массива предотвращает лишний diffing дочерних компонентов.

2. **Ограничения `v-memo`**:
   - `v-memo` эффективен для тяжелых списков, но требует строгой точности. Если забыть передать поле (например, `task.title`), интерфейс перестанет обновляться при изменении этого поля.

3. **`shallowRef` для массивов**:
   - При загрузке и полной замене больших массивов с бэкенда `shallowRef` исключает создание глубинного Proxy для каждого поля объекта, уменьшая расход памяти и ускоряя монтирование.

### Реализованные оптимизации Core Web Vitals

1. **CLS (Cumulative Layout Shift)**:
   - Зарезервирована минимальная высота контейнера (`min-height: 650px`) для предотвращения схлопывания UI.
   - Добавлены скелетоны Naive UI (`NSkeleton`) на время асинхронной загрузки данных из Pinia.

2. **INP / TBT (Total Blocking Time & Responsiveness)**:
   - Массив задач в Pinia переведен на `shallowRef`, предотвращающий глубокое обёртывание объектов в Proxy.
   - Добавлен `debounce` (300 мс) на поиск для предотвращения Long Tasks при вводе.

3. **Re-renders & Virtualization**:
   - Для карточек списка внедрены Prop Stability (`:is-selected`) и директива `v-memo`.
   - При переключении или редактировании одной задачи перерисовывается только целевая карточка, а не весь массив.

4. **Инфраструктура `index.html`**:
   - Настроен корректный атрибут `lang="ru"`, мета-тег `viewport` и заголовок приложения.
