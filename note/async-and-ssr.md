## 1. Карта фоновых задач

| Задача                              | Что делает                                            | Триггер                                | Ретраи                                         | Идемпотентна ли                                             | Что будет, если упадёт                                                                                   |
| :---------------------------------- | :---------------------------------------------------- | :------------------------------------- | :--------------------------------------------- | :---------------------------------------------------------- | :------------------------------------------------------------------------------------------------------- |
| `send_welcome_email_idempotent`     | Отправляет приветственное письмо пользователю         | Регистрация пользователя / Вызов View  | До 3 раз (экспоненциальная задержка)           | **Да** (ключ `welcome_email_sent:{user_id}` в Redis)        | Письмо не отправится сразу, сделает до 3 попыток, затем залогирует ошибку. ## 2. Правило границы (Sync vs Async)

**Критерий:** Если выполнение операции занимает > 200мс, зависит от внешних сетевых сервисов (SMTP, Webhook, REST API) или её сбой не должен блокировать выдачу HTTP-ответа пользователю — операция уходит в очередь Celery.

- **Синхронно:**
  - Валидация входных данных HTTP-запроса.
  - Быстрые CRUD-операции в PostgreSQL (создание, чтение, обновление в рамках < 50мс).
  - Проверка прав доступа (Permissions) и аутентификация.
- **Асинхронно (В очередь):**
  - Отправка Email / Push / SMS уведомлений.
  - Взаимодействие со сторонними HTTP API (webhooks, интеграции).
  - Фоновая очистка, агрегация статистики, генерация отчетов.

## 3. Стратегия повторов (Retry Policy)

### Что ретраим:

- `RequestException`, `HTTPError`, `ConnectionError`, `Timeout`: Временные сетевые сбои или недоступность внешних сервисов.
- `SoftTimeLimitExceeded`: Превышение мягкого лимита времени (даем возможность аккуратно завершить задачу или перезапустить).
- `OperationalError` (БД / Redis): Кратковременные моргания сети между сервисами.

### Что НЕ ретраим:

- `DoesNotExist` (`User.DoesNotExist`, `Task.DoesNotExist`): Если объекта нет в БД, повторные запуски его не создадут.
- `ValueError`, `TypeError`, `ValidationError`: Ошибки в коде или некорректные аргументы задачи (неисправимы повторными запусками).

## 4. Инфраструктура

### Сервисы

- **`redis`**: In-memory брокер сообщений и бэкенд результатов / кэш идемпотентности.
- **`celery_worker`**: Обработчик фоновых задач (выполняет кодовую базу `apps.users.tasks` и `apps.tasks.tasks`).
- **`celery_beat`**: Планировщик периодических задач (singleton, отправляет задачи в Redis по расписанию).
- **`flower`**: Веб-интерфейс для мониторинга состояния очередей и воркеров (порт `5555`).

### Запуск и логи

```bash
# Запуск всей инфраструктуры
docker compose up -d

# Просмотр логов воркера
docker compose logs -f celery_worker

# Просмотр логов планировщика
docker compose logs -f celery_beat

# Просмотр логов Flower
docker compose logs -f flower
```

## 5. Мониторинг и Инциденты

- **Flower (`http://localhost:5555`):**
  - Раздел **Workers**: Статус воркеров (должен быть `Online`), количество активных процессов.
  - Раздел **Tasks**: Просмотр состояния задач (`SUCCESS`, `FAILURE`, `RETRY`), аргументов и Traceback ошибок.
- **Критерии инцидента:**
  - Воркер перешел в статус `Offline`.
  - Доля упавших задач (`FAILURE`) превышает 5% за последние 15 минут.
  - Длина очереди задач в Redis непрерывно растет (воркер не успевает разбирать таски).
  - Появление ошибок `SoftTimeLimitExceeded` в логах.

## 6. Frontend-абстракции (Vue 3 / Nuxt 3)

- **Renderless-компоненты:** Применяются для инкапсуляции состояния и логики без привязки к верстке (обертки для пагинации, обработки форм, подписки на WebSocket).
- **`<component :is>`:** Используется для динамического переключения табов в панели управления, пошаговых мастеров (Wizards) и виджетов дашборда.
- **Async-компоненты (`defineAsyncComponent`):** Применяются для тяжелых модальных окон, интерактивных графиков (Chart.js/ECharts) и WYSIWYG-редакторов для уменьшения стартового бандла.
- **Правило выноса:** Компонент выносится в абстракцию, если он превышает ~200 строк кода, либо его UI/state-логика повторно используется в ≥2 местах приложения.

## 7. SSR: Вывод и результаты исследований

### Результаты экспериментов (SPA vs Nuxt 3 SSR)

1. **View Source:**
   - **SPA (Vue 3 + Vite):** Отдаёт пустой `<div id="app"></div>`. Контент рендерится на клиенте после загрузки JS-бандла.
   - **SSR (Nuxt 3):** Отдаёт сформированный HTML со всеми данными и сериализованным состоянием `__NUXT_DATA__`.
2. **Hydration Mismatch:**
   - Воспроизведен через `Math.random()` и разницу часовых поясов. Продемонстрировал расхождение серверного HTML и клиентского DOM.
3. **Server Engine:**
   - Протестирован серверный роут `/api/tasks` через встроенный Nitro-сервер.

### Итоговое решение

Проект представляет собой закрытую панель управления (Dashboard) с обязательной аутентификацией и приватными данными.

- **SEO-индексация не требуется** (все страницы находятся за авторизацией).
- **SSR усложняет инфраструктуру** (требуется отдельный Node.js-сервер вместо отдачи статики через Nginx) и вносит риски ошибок гидратации.

**Решение:** Оставить текущую **SPA-архитектуру (Vue 3 + Vite)**.
**Условия возврата к SSR:** Появление публичных страниц приложения, требующих индексации поисковыми системами (SEO-лендинги, публичный блог, документация).

## 8. Технический долг

1. **Dead-Letter Queue (DLQ):** Настройка отдельной очереди для задач, исчерпавших лимит ретраев (`max_retries`), для их дальнейшего ручного разбора.
2. **Алертинг:** Интеграция Sentry / Telegram Bot для немедленного оповещения при падении задач.
3. **Разделение очередей:** Выделение отдельной очереди (`heavy_tasks`) для длительных операций с выделением изолированных воркеров.
